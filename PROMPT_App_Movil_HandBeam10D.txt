================================================================================
CONTEXTO DEL HARDWARE — ESP32-2432S032 (LEER ANTES DE PROGRAMAR)
================================================================================

El dispositivo objetivo es el módulo ESP32-2432S032 con las siguientes
especificaciones confirmadas por documentación oficial del fabricante:

MICROCONTROLADOR:
- Chip: ESP32-WROOM-32 (Espressif)
- CPU: Dual-core Tensilica LX6, 240 MHz, 600 DMIPS
- RAM: 520 KB SRAM
- Flash: 4 MB
- WiFi: 802.11 b/g/n HT40 integrado (2.4 GHz)
- Bluetooth: BLE 4.2 + Classic integrado

DISPLAY (no relevante para la app, pero sí para el firmware del ESP32):
- Pantalla: ST7789 IPS 3.2" — 240×320 px — interface SPI
- Touch: GT911 capacitivo — I2C — hasta 5 puntos

CAPACIDADES WiFi CONFIRMADAS (por demos oficiales del fabricante):
- Modo AP (Access Point): el ESP32 crea su propia red WiFi
  → SSID configurable, contraseña configurable
  → IP por defecto del AP: 192.168.4.1
  → Hasta 4 clientes simultáneos
- Modo STA (Station): el ESP32 se conecta a un router externo
- Servidor TCP: puerto configurable, comunicación raw
- Servidor HTTP: responde peticiones GET/POST como un servidor web estándar
- Modo híbrido AP+STA: puede usarse simultáneamente

PROTOCOLO ELEGIDO PARA ESTA APP: HTTP REST sobre WiFi
Justificación basada en los demos oficiales:
- El demo 4_7 del fabricante implementa un servidor HTTP completo en el ESP32
  que responde peticiones GET con parámetros en la URL
- El demo 4_4 muestra servidor TCP con lectura de datos del cliente
- HTTP es compatible nativamente con cualquier framework móvil (Flutter, React Native)
- No requiere librerías externas en el lado móvil
- Las peticiones son texto plano (JSON), fáciles de parsear en el ESP32
- Permite enviar múltiples parámetros en una sola petición

================================================================================
PROTOCOLO DE COMUNICACIÓN ESP32 ↔ APP
================================================================================

El ESP32 corre en MODO AP (Access Point):
- SSID: "HandBeam10D"
- Password: "laser2024" (configurable en el firmware)
- IP del ESP32: 192.168.4.1
- Puerto HTTP: 80

El móvil se conecta a esa red WiFi y envía peticiones HTTP.

ENDPOINT PRINCIPAL — Enviar parámetros de tratamiento:
  POST http://192.168.4.1/tratamiento
  Content-Type: application/json

  Body JSON:
  {
    "tiempo": 180,
    "rojo": true,
    "violeta": false,
    "infrarrojo": true,
    "nm_rojo": 650,
    "nm_violeta": 405,
    "nm_infrarrojo": 850,
    "afeccion": "Dolor articular"
  }

ENDPOINT — Consultar estado actual:
  GET http://192.168.4.1/estado

  Respuesta JSON del ESP32:
  {
    "estado": "corriendo",
    "tiempo_restante": 120,
    "tiempo_total": 180,
    "rojo": true,
    "violeta": false,
    "infrarrojo": true
  }

ENDPOINT — Detener tratamiento:
  POST http://192.168.4.1/detener

ENDPOINT — Pausar tratamiento:
  POST http://192.168.4.1/pausar

ENDPOINT — Reanudar tratamiento:
  POST http://192.168.4.1/reanudar

ENDPOINT — Ping / verificar conexión:
  GET http://192.168.4.1/ping
  Respuesta: { "ok": true, "dispositivo": "HandBeam10D" }

=== ARQUITECTURA DE COMUNICACIÓN CON EL ESP32 ===

El ESP32-2432S032 opera en modo WiFi Access Point (AP):
  SSID del ESP32: "HandBeam10D"
  Contraseña:     "laser2024"
  IP del ESP32:   192.168.4.1
  Puerto:         80
  Protocolo:      HTTP/1.1 con body JSON

El usuario conecta el móvil a la red "HandBeam10D" antes de abrir la app.
La app detecta si está conectada a esa red WiFi específica antes de habilitar
los controles de tratamiento. Si no está conectada, muestra la pantalla de
instrucciones de conexión.

ENDPOINTS que la app debe consumir:

  1. GET  http://192.168.4.1/ping
     → Verifica conexión. Respuesta: {"ok":true,"dispositivo":"HandBeam10D"}

  2. POST http://192.168.4.1/tratamiento
     Content-Type: application/json
     Body: {
       "tiempo": <int, segundos>,
       "rojo": <bool>,
       "violeta": <bool>,
       "infrarrojo": <bool>,
       "nm_rojo": 650,
       "nm_violeta": 405,
       "nm_infrarrojo": 850,
       "afeccion": "<string, nombre de la afección>"
     }
     Respuesta éxito: {"ok":true,"mensaje":"Tratamiento iniciado"}
     Respuesta error: {"ok":false,"error":"<descripción>"}

  3. GET  http://192.168.4.1/estado
     Respuesta: {
       "estado": "corriendo" | "pausado" | "detenido" | "finalizado",
       "tiempo_restante": <int, segundos>,
       "tiempo_total": <int, segundos>,
       "rojo": <bool>,
       "violeta": <bool>,
       "infrarrojo": <bool>
     }

  4. POST http://192.168.4.1/detener
     → Detiene el tratamiento en curso.

  5. POST http://192.168.4.1/pausar
     → Pausa el countdown en el ESP32.

  6. POST http://192.168.4.1/reanudar
     → Reanuda el countdown pausado.

Implementa un polling cada 2 segundos al endpoint /estado cuando hay un
tratamiento en curso, para sincronizar el progreso en tiempo real.
Usa un timeout de 3 segundos en todas las peticiones HTTP.
Maneja los errores de red con mensajes claros en español al usuario.

=== CÓDIGO DEL FIRMWARE ESP32 QUE DEBES GENERAR TAMBIÉN ===

Además de la app Flutter, genera el código Arduino/C++ completo para el
firmware del ESP32 que implemente el servidor HTTP descrito. El firmware debe:

1. Configurar WiFi en modo AP con SSID "HandBeam10D" y password "laser2024"
2. Arrancar un servidor HTTP en el puerto 80
3. Responder los 6 endpoints descritos con JSON válido
4. Integrar con el sistema de variables globales de LVGL/EEZ Studio ya
   existente en el proyecto (variables: is_running, treatment_time, check_R,
   check_V, check_IR, show_notification, notification_text)
5. Cuando recibe POST /tratamiento:
   - Actualizar las variables: check_R, check_V, check_IR, treatment_time
   - Establecer is_running = true
   - Actualizar notification_text con el nombre de la afección
   - Activar show_notification por 2 segundos
6. Cuando recibe POST /detener: is_running = false, treatment_time = 0
7. Cuando recibe POST /pausar: is_running = false (sin resetear el tiempo)
8. Cuando recibe POST /reanudar: is_running = true
9. GET /estado devuelve el estado actual de todas las variables relevantes
10. Permitir CORS en todas las respuestas para evitar errores de política

El servidor HTTP debe funcionar en un FreeRTOS task separado (Core 0) para
no interferir con el rendering de LVGL que corre en Core 1.
Usar la librería WiFi.h nativa del ESP32 Arduino Core 3.3.5.
